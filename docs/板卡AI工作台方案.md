# Edge SSH AI：板卡 AI 工作台方案

状态：原始设计建议。2026-11-03 用户已确认第一版采用单 Linux 账号，并暂不接入 codebody；下文多账号建议仅作未来备选。当前实现与验证以根目录 README.md 和第一版验证记录.md 为准。

## 目标与边界

在 Windows 上管理 LPB3568 等 Linux 板卡，完成设备检测、编程助手安装、模型 API 配置、代理连接、诊断和 VS Code Remote SSH 启动。

默认场景是“编程助手运行在板卡，模型通过云端 API 或受支持的登录方式提供服务”。板卡本地运行模型是独立的扩展能力，需要额外评估内存、模型规模、推理框架和 NPU 适配，不能由 RK3568 型号直接推定可用。

## 现有代码的结论

可复用：

- `LPB3568codex/start-codex-QMB3568.ps1`：SSH 检测、本机代理检测、反向转发和打开 VS Code 的流程。
- `repair.py`、`remote_repair.py`、`jsonc_utils.py`：服务端检查、下载安装包校验、备份及 JSONC 配置修改。

需要重新设计：

- API 和 Plus 切换脚本都覆盖同一账号的 `~/.codex/config.toml`、认证文件和 `~/.vscode-server/server-env-setup`；Plus 脚本还修改 `.profile`、`.bashrc`。修复程序添加的代理检查块可能被后续模式切换覆盖。
- 两个切换脚本和停止脚本使用宽泛的 `pkill -u FineHigh -f ...`，同账号下其他人的 VS Code 和 Codex 会受到影响。
- 停止脚本通过 `taskkill /F /T /IM Code.exe` 关闭本机所有 VS Code 窗口。
- 清理 `/tmp/code-*`、`/tmp/vscode-*` 和 `/tmp/codex-ipc` 没有按具体会话隔离。
- 反向代理固定占用板卡 `127.0.0.1:7890`。另一台电脑不能再独立绑定相同监听地址，现有隧道的退出也会影响依赖它的客户端。
- 设备别名、账号、工程路径、供应商和部分版本被硬编码。
- 网络检查不足以证明模型可用：API 模式接受任意 1xx—5xx 状态；代理检查也没有验证成功的认证与推理请求。

这些是源码可以确认的冲突风险，并非对历史卡顿的唯一根因诊断。仍需真实的 Remote SSH 日志、板卡系统信息及资源检查。

## 推荐架构

Windows 管理界面 → 本机任务与凭据管理 → OpenSSH → 板卡用户环境 → 工具适配器 → 模型供应商。

### 用户和工作环境

每个人使用独立 Linux 账号，独立 HOME、SSH 密钥、VS Code Server、工具认证、缓存和日志。需要共享代码时通过 Unix 组与明确的目录权限完成；建议各自检出或使用工作树，避免同时编辑同一工作目录。

Linux 账号隔离不能隔离 CPU、内存、磁盘和所有系统服务；设备资源压力仍需检测，必要时再加入资源限制。

仅建立不同 SSH 别名，仍登录同一个 FineHigh，并不能隔离远程环境。工具配置目录隔离可作为过渡，但不能替代多人账号隔离，也不能假设所有 IDE 扩展都支持自定义配置目录。

### 代理

每个受管连接拥有独立的板卡回环监听端口和本机隧道进程记录。端口分配以 SSH 实际绑定成功为准，冲突时更换并重试；不能只依靠绑定前探测。

代理环境默认只注入受管工具进程。若 IDE 插件需要整个扩展宿主的代理，使用独立用户环境，并验证插件实际读取环境的方式。避免把个人电脑的代理永久写入共享登录脚本。

本机管理程序负责隧道存活检测、退避重连和明确的断线提示。关闭管理程序或本机代理后，依赖这条线路的请求仍会中断；需要持续可用时可配置独立常驻代理主机或可直连 API。

仅结束自己创建且经过身份核验的子进程；不按进程名批量终止。板卡监听保持在回环地址，SSH 主机密钥应首次核验并固定，后续变更明确报错。

### 工具与供应商分离

“工具”负责读写项目、调用命令和执行编程任务；“供应商”负责提供模型推理。界面分别选择二者。

每个工具适配器声明：安装来源、架构及系统库要求、固定版本、配置格式、凭据存储方式、支持的 API 协议、网络设置、健康检查、CLI/IDE 接入能力与卸载范围。

工具初始范围：

| 工具 | 计划 | 待确认事项 |
| --- | --- | --- |
| Codex | 第一阶段接入 | 当前版本、板卡兼容性、认证及配置方式、目标 API 协议 |
| DeepSeek Harness | 用户确认项目为 https://github.com/deepseek-ai/deepseek-harness | 实际安装流程、依赖、ARM64、API 配置、IDE 接入能力 |
| codebody | 预留适配器 | 项目完整名称或链接尚未确认 |

不保证任意兼容 OpenAI 的 API 都能用于任意助手。需要分别验证 Responses、Chat Completions 等协议，以及流式响应、工具调用、错误格式和模型能力。VS Code 插件也应验证实际运行位置与支持的后端；终端可运行不代表某个插件能直接接入。

### 检测与修复

按层显示结果：局域网与 SSH → 身份认证 → 系统与资源 → VS Code Server → 工具安装 → API 网络 → API 认证 → 最小推理 → IDE 功能。

先进行只读诊断；涉及重启或配置修改时展示目标用户、版本、文件、会话影响和备份。执行后重新验证目标功能。不得仅以打开窗口或 HTTP 端口可达判定成功。

API 验证分两级：无模型请求的网络/认证检查，以及用户主动触发的最小推理测试，后者显示可能产生少量调用费用。错误按 TLS、DNS、401/403、限额、模型不存在、协议不兼容等归类，并保留经过脱敏的诊断信息。

凭据通过 Windows Credential Manager 等系统凭据设施保存。需要在板卡持久化的凭据按工具支持方式处理，限制文件权限；不能宣称 API Key 永远只在电脑上。日志、配置导出和诊断包必须脱敏。

## 界面与使用路径

主导航建议：设备、工作环境、AI 工具、模型服务、网络、诊断。

首次使用：添加设备 → 核验 SSH 主机指纹 → 登录与系统检测 → 设置独立用户环境 → 选择工具 → 配置供应商 → 验证 → 打开 VS Code。

设备详情页展示 IP/账号、架构、系统库兼容性、磁盘与内存、SSH、VS Code Server、隧道和工具状态。常用操作是“连接”“打开 VS Code”“测试 AI”“诊断”，不要求用户理解脚本执行顺序。

配置变更先展示差异；安装、升级、回滚和修复作为有状态任务执行。每个任务记录阶段、结果、影响范围与可恢复信息，长任务不得阻塞界面。

## 实施顺序

1. 验证 LPB3568 基线：只读获取系统、架构、glibc、内存、空间、SSH/VS Code 日志和现有配置关系；保存脱敏诊断。
2. MVP：Windows 中文图形界面、设备管理、分层诊断、独立 SSH 配置管理、单一工具 Codex、API 配置测试、受管代理、一键打开 VS Code。
3. 多人使用：独立账号引导、共享项目权限、两个客户端同时连接和互不影响的生命周期测试。账号创建需管理员权限，作为单独部署操作。
4. 多工具：验证并接入 DeepSeek Harness；明确 codebody 项目后再接入。增加工具版本固定和配置回滚。
5. 扩展：多板卡、配置模板、离线安装包、持续连接的常驻代理主机，以及按实际必要性增加板卡服务。

技术建议：首版使用 Python + PySide6，复用现有 Python 能力，调用系统 OpenSSH；UI 与任务执行及工具适配器分离。板卡尽量使用已有 SSH 和轻量脚本，不先引入 Docker、常驻 Web 服务或统一 API 转换网关。打包后在没有开发环境的 Windows 上验证安装与运行。

## 验收标准

- 新电脑无需手动改脚本即可添加设备、完成检测并打开目标工程。
- 两个用户同时连接，某一用户停止工具、断开代理或修改供应商，不结束另一用户的 VS Code 或覆盖其认证配置。
- 代理关闭时明确显示依赖失效，SSH 与编辑能力不因代理地址失效而被错误判为不可用。
- 已有完整且匹配的 VS Code Server 可复用；修复限于明确目标和版本，并保留备份。
- API 测试分别报告网络、认证和推理结果；错误协议或模型配置不能显示为成功。
- ARM64、系统库或资源不足时，在安装前明确给出不支持原因；不保证所有 Linux 板卡都可安装所有工具。
- 安装失败后可定位已完成的阶段、保留日志并恢复受管配置；卸载只处理本工具管理的资源。
- 导出的诊断信息不含密码、API Key、访问令牌或认证文件内容。
